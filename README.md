# Arcades Profile

Personal site, portfolio, and publishing system for [thearcades.me](https://thearcades.me).
The application runs Next.js 15 and React 19 alongside Payload CMS v3, with
PostgreSQL for content, Vercel Blob for media, Postmark for outbound email, and
ActiveCampaign for subscriber and audience management.

## Architecture

Next.js App Router and Payload share one application. Route groups keep their
responsibilities separate without adding group names to public URLs:

- [`app/(frontend)/`](app/(frontend)/) contains the public site, RSS feed, and
  hand-written REST endpoints. Add custom API routes under
  `app/(frontend)/api/`.
- [`app/(payload)/`](app/(payload)/) mounts the generated Payload admin at
  `/admin` and Payload's REST/GraphQL catch-all under `/api`. Do not add
  hand-written routes here; they can collide with Payload's catch-all.
- [`payload.config.ts`](payload.config.ts) is the Payload composition root. It
  configures PostgreSQL, the Lexical editor and YouTube block, email, media
  storage, collections, globals, and generated types.
- [`collections/`](collections/) contains Payload collection definitions and
  shared fields, access helpers, and lifecycle hooks. The registry is
  [`collections/index.ts`](collections/index.ts); the publishing queue global is
  registered there from [`globals/PublishQueue.ts`](globals/PublishQueue.ts).
- [`collections/Media.ts`](collections/Media.ts) defines image variants and
  metadata. The Vercel Blob adapter in `payload.config.ts` stores the actual
  media objects.
- [`payload-types.ts`](payload-types.ts) is generated by Payload. Import it
  through `@/payload-types`; do not edit it by hand.

The `@/*` path alias resolves from the repository root, and `@payload-config`
resolves to `payload.config.ts`.

## Local development

Use Node.js 20 and npm only. CI also runs on Node 20; do not substitute yarn,
pnpm, or bun.

```bash
npm install
cp .env.example .env.local
npm run dev
```

The site and Payload admin are then available at:

- Public site: <http://localhost:3000>
- Payload admin: <http://localhost:3000/admin>

Copy [`.env.example`](.env.example) as the starting inventory of service
configuration. Put real local values in `.env.local`, which is ignored by Git,
and never commit or paste secrets into documentation. At minimum, configure the
services needed for the workflow you are exercising:

- `DATABASE_URL` (or the application-level alias `DATABASE_URI`) for
  PostgreSQL-backed CMS and migration work.
- `PAYLOAD_SECRET` as a high-entropy value in production. Development has an
  explicit development-only fallback.
- `BLOB_READ_WRITE_TOKEN` for Payload media uploads to Vercel Blob.
- Postmark and ActiveCampaign variables for email and subscription workflows.
- `CRON_SECRET` for authenticated cron-style endpoints.
- Payload and MCP API keys when using the MCP server.

Payload config deliberately disables development schema push. Dev can boot
without a configured database URL, but CMS/database operations require a real
connection.

## Database migrations

Schema changes under `collections/` require a checked-in Payload migration. A
migration must export both `up()` and `down()`; use a documented no-op `down()`
when data cannot be safely restored, and guard SQL with `IF EXISTS` or
`IF NOT EXISTS` where appropriate. See
[`migrations/README.md`](migrations/README.md) for the creation and snapshot
workflow.

```bash
# Apply pending migrations; loads .env.local
npm run migrate

# Inspect Payload migration status
npx payload migrate:status

# PR guard: collection changes must include a migration
npm run check:migrations

# Audit migrations/index.ts registration
npm run check:migration-index
```

`npm run migrate` loads `.env.local`. Direct `npx payload migrate:*` commands
require `DATABASE_URL` or `DATABASE_URI` to be exported or supplied inline.
The diff-based `check:migrations` command is primarily a CI command and needs
the PR base/head range (`BASE_SHA` and `HEAD_SHA`, or the equivalent positional
arguments). The `[skip-migration-check]` commit token is only for collection
edits that do not change schema, such as hooks, access rules, labels, or
descriptions.

On Vercel, [`vercel.json`](vercel.json) guards database setup with
`DATABASE_URL`. When it is present, the build runs the idempotent
`npm run db:bootstrap` repair step and then applies migrations before
`npm run build`; without it, both database steps are skipped and the Next.js
build still runs. Set `DATABASE_URL` in Vercel even though application code also
accepts `DATABASE_URI`.

## Publishing

Posts use four workflow states defined in [`lib/post-status.ts`](lib/post-status.ts):

1. `draft` — not queued and not public.
2. `scheduled` — queued with a future `scheduledPublishDate`. Saving a draft
   with a scheduled date promotes it to this state; validation rejects a
   scheduled post without a valid future date.
3. `published` — public. The scheduler moves due posts here and writes a
   pending, read-only `newsletterSend` state before attempting delivery.
4. `sent` — the per-post newsletter send was accepted by Postmark. Detailed
   submission, delivery, bounce, open, click, complaint, failure, and
   reconciliation state remains in `newsletterSend`.

The [`Publish scheduled posts`](.github/workflows/scheduled-posts.yml) GitHub
Actions workflow runs every 15 minutes (with normal hosted-scheduler jitter)
and sends:

```text
POST /api/posts/publish-scheduled
Authorization: Bearer <CRON_SECRET>
```

The route authenticates through [`lib/cronAuth.ts`](lib/cronAuth.ts) and invokes
[`publishScheduledPosts`](lib/publishScheduled.ts). The publisher self-heals
queue dates, promotes due posts, attempts the newsletter, retries eligible
failed or stale pending sends on later runs, and reports stuck or undelivered
records. A per-run cap can be set with `SCHEDULED_POSTS_PER_RUN`.

`suppressNewsletter` skips the per-post send and records a suppressed
newsletter state; the post remains `published`. Other skipped or failed sends
also remain public rather than pretending that delivery succeeded.
`newsletterSend` is operational state written by the publishing and Postmark
event pipeline, not an editor-maintained field.

Canonical post URLs belong to [`lib/post-url.ts`](lib/post-url.ts). Use
`buildPostUrl`, `buildGroupIntroUrl`, and `computePostPartIndex` instead of
assembling project URLs or deriving part numbers inline. Collection lifecycle
hooks use [`collections/hooks/revalidate.ts`](collections/hooks/revalidate.ts)
to invalidate the affected post/group URLs plus index and feed paths after
changes or deletions.

## Email and audience ownership

The boundary is deliberate:

- **Postmark sends email.** Payload auth mail, transactional/test mail, preview
  sends, and per-post newsletters all leave the application through Postmark.
  The main delivery code is in [`lib/postmark.ts`](lib/postmark.ts),
  [`lib/payload-email.ts`](lib/payload-email.ts), and
  [`lib/post-newsletter-delivery.ts`](lib/post-newsletter-delivery.ts).
- **ActiveCampaign owns marketing state.** Contacts, list membership,
  subscription/consent state, segmentation, and audience selection live in
  ActiveCampaign. [`app/(frontend)/api/subscribe/route.ts`](app/(frontend)/api/subscribe/route.ts)
  synchronizes list membership there. A post send resolves active recipients
  from the configured All plus Fiction/Essays lists, deduplicates them, and
  hands delivery to Postmark.

Do not create a new ActiveCampaign campaign/email-send path for site mail.
Resolve the audience from ActiveCampaign, then deliver with Postmark.

Accepted Postmark messages are recorded in the `postmark-events` collection.
`POST /api/postmark/webhook` updates the post-level `newsletterSend` aggregates;
the webhook must be configured on the Postmark broadcast stream for those
delivery and bounce counts to advance.

## Payload MCP server

[`mcp/tools.ts`](mcp/tools.ts) is the single registry for MCP tool definitions,
handlers, and read/write scopes. Register a tool there so both transports expose
the same implementation:

- [`mcp/payload-mcp.ts`](mcp/payload-mcp.ts) is the stdio entry point for local
  clients.
- [`app/(frontend)/api/mcp/route.ts`](app/(frontend)/api/mcp/route.ts) is the
  stateless HTTP/SSE-compatible transport at `POST /api/mcp`.

Start the local Next.js server first, configure `PAYLOAD_API_URL` and a Payload
user API key, then run:

```bash
npm run mcp
```

The checked-in [`.mcp.json`](.mcp.json) points local clients at the same stdio
entry point. Do not commit a real `PAYLOAD_API_KEY` into that file.

HTTP transport authentication is separate from Payload API authentication:

- `MCP_API_KEY` / `MCP_API_KEYS` are write keys and may invoke any registered
  tool.
- `MCP_READ_KEY` / `MCP_READ_KEYS` are read-only keys and may invoke only tools
  classified as reads (currently `list_*` and `get_*`).

Plural variables are comma-separated rotation sets. `MCP_API_KEY` is not
`PAYLOAD_API_KEY`; rotate and store them independently.

## Verification

Install dependencies before running checks. The standard commands are:

```bash
# Next.js ESLint command
npm run lint

# Strict TypeScript check used by CI
npx tsc --noEmit

# All node:test suites under lib/, collections/, and mcp/
npm test

# Production Next.js build
npm run build

# One focused node:test file
npx tsx --test lib/newsletter.test.ts
```

Tests use Node's built-in test runner through `tsx`; there is no Jest or Vitest.
Focused tests can target any `*.test.ts` file in the tested directories. Build
and integration behavior that touches Payload, PostgreSQL, Blob, Postmark, or
ActiveCampaign requires the relevant environment configuration; never use
production secrets merely to satisfy a local documentation or unit-test check.

## Deployment

The application deploys to Vercel:

- `npm install` is the configured install command and `.next` is the output.
- PostgreSQL is the Payload database.
- Vercel Blob stores media uploaded through the `media` collection.
- With `DATABASE_URL` set, guarded bootstrap and migrations run before every
  Vercel build as described above.
- Production and preview configuration belongs in Vercel environment settings.
  Copy variable names from `.env.example`, not values from another environment,
  and verify the target scope when adding or rotating a secret.

Deployment, migration against shared databases, webhook registration, and live
email sends are operational actions. Run them only with explicit authorization
and against the intended Vercel environment.
