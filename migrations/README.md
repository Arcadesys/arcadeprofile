# Migrations

Payload migrations live in this directory and are applied with:

```bash
npm run migrate
```

The migration index (`index.ts`) is regenerated by Payload when you create a new migration via the CLI; it's checked in.

## Adding a migration

Prefer the CLI:

```bash
DATABASE_URL=... npx payload migrate:create --name <descriptive_name>
```

It diffs your current Payload config against the latest `*.json` snapshot in this directory and writes three things:

1. `migrations/<timestamp>_<name>.ts` — generated SQL for the diff
2. `migrations/<timestamp>_<name>.json` — fresh schema snapshot (the baseline for the *next* `migrate:create`)
3. `migrations/index.ts` — regenerated to import the new file

Commit all three.

For renames, data backfills, or anything Drizzle can't infer, hand-roll the `.ts` file using the same filename pattern (`YYYYMMDD_HHMMSS_<short-description>.ts`). After hand-rolling, still run `payload migrate:create --skip-empty` so the snapshot and `index.ts` stay current.

`migrate:create` is filesystem-only — it reads the Payload config and writes files. It needs a `DATABASE_URL` to boot Payload, but it does not query or modify the database.

## Conventions

### Always export `down()`

Every migration must export both `up()` and `down()`. If a rollback isn't safely reversible — e.g. you dropped a table whose data was sourced elsewhere — make `down()` a documented no-op rather than skipping it:

```ts
export async function down(_args: MigrateDownArgs): Promise<void> {
  // Subscriber data lived in ActiveCampaign as the source of truth after
  // this migration; rebuilding the table here would not repopulate it.
  // Intentionally a no-op.
}
```

The point is to make the rollback story **visible at review time**, not to guarantee it always rebuilds data.

### Be explicit with destructive statements

Use `IF EXISTS` / `IF NOT EXISTS` guards so a migration replayed against a partially-migrated database doesn't crash:

```sql
DROP TABLE IF EXISTS "subscribers" CASCADE;
ALTER TABLE "users" DROP COLUMN IF EXISTS "legacy_field";
```

For schema changes that touch large tables in production, consider:

1. Splitting into a multi-step migration (add new column → backfill → drop old) so each step is reversible.
2. Verifying the migration locally against a representative dataset before deploying.
3. Coordinating with anyone running the staging admin so the schema change doesn't surprise an in-progress edit.

### Migration filenames

`YYYYMMDD_HHMMSS_<short-description>.ts`. Payload generates this format automatically; preserve it for new files so the index stays sortable.

## Running locally

```bash
# Apply all pending migrations
npm run migrate

# See current migration status (via Payload CLI)
npx payload migrate:status
```

`DATABASE_URL` (or `DATABASE_URI`) must be set for any of these to work; `payload.config.ts` will throw at boot otherwise.

## CI guards

Two automated checks run on every PR (see `.github/workflows/ci.yml` → `migrations-check` job):

### `npm run check:migrations`

Diff-based heuristic ([scripts/check-migrations.mjs](../scripts/check-migrations.mjs)). Fails if any file under `collections/` changes in the PR range and no new `migrations/<timestamp>_*.ts` is added.

Escape hatch: include `[skip-migration-check]` in any commit message in the PR for non-schema collection edits (admin labels, hooks, descriptions, access functions).

### `npm run check:migration-index`

Registration audit ([scripts/check-migration-index.mjs](../scripts/check-migration-index.mjs)). Replicates Payload's `writeMigrationIndex` byte-for-byte and fails if `migrations/index.ts` doesn't match what `payload migrate:create` would produce. Catches the bug class where a migration `.ts` file is added to disk but missing from `index.ts` (so `payload migrate` silently skips it in production).

Fix is always: `DATABASE_URL=... npx payload migrate:create --skip-empty` and commit the regenerated `index.ts`.

## Refreshing the snapshot baseline

`payload migrate:create` reads the alphabetically-latest `.json` in this directory as its diff baseline. If the baseline gets stale (many migrations land without snapshots), drizzle-kit's diff produces dozens of interactive rename-vs-create prompts that don't accept piped stdin cleanly, making the CLI effectively unusable.

To refresh, use [scripts/write-baseline-snapshot.mjs](../scripts/write-baseline-snapshot.mjs) — it writes the snapshot directly via `adapter.requireDrizzleKit().generateDrizzleJson(adapter.schema)`, no diff, no prompts:

```bash
# 1. Write a fresh snapshot named to match the latest registered migration
#    (so it sorts last and Payload picks it up as the diff baseline).
DATABASE_URL=... npx tsx --require ./scripts/patch-next-env.cjs \
  scripts/write-baseline-snapshot.mjs \
  migrations/<latest-existing-migration-timestamp>.json

# 2. Sanity-check: with a fresh baseline, --skip-empty should exit clean
#    (drift between snapshot and config is zero).
DATABASE_URL=... npx payload migrate:create --skip-empty --name sanity
# No files written.

# 3. Verify the registration audit still passes (this script doesn't touch index.ts).
npm run check:migration-index
```

Commit just the one new `.json` file. Although `migrate:create` requires a live `DATABASE_URL` to boot Payload, neither this procedure nor `migrate:create` itself writes to the database.
